> **문서 유형:** 기존 `TOWERGLIDE_Unity_ClaudeCode_SuperPrompt.md`에 추가하는 확장 명세(Add-on)
>
> **목표:** 비행기 조종 게임 TOWERGLIDE의 핵심을 유지하면서, 제한된 800m × 800m 테스트 맵을 서울을 배경으로 한 구역 스트리밍형 오픈월드로 단계적으로 확장한다.

> **엔진:** 기존 명세 유지 — Unity 6.3 LTS + URP + C#
>
> **플랫폼:** Android 우선, PC 에디터 테스트 병행
>
> **개발/배포 가정:** 개인 학습·비상업적 프로젝트 우선. 공개 배포를 하게 되면 지도·모델·음원·상표의 라이선스를 다시 검토한다.

# 0. 기존 SuperPrompt와의 적용 관계

이 문서는 기존 TOWERGLIDE SuperPrompt를 대체하지 않는 **추가 명세**다. 기존 명세의 비행 물리, 비행기 조작, 카메라, 장애물, 점수, HUD, 로컬 저장, Android 최적화, 무료 에셋 우선 원칙은 유지한다.

다만 아래 월드 범위와 레벨 설계에 관한 내용은 이 추가 명세가 우선한다.

1. 기존 명세의 `800m × 800m`는 최종 월드 크기가 아니라 **초기 스트리밍·비행 검증용 테스트 청크**로 재정의한다.
2. 기존의 “무한 오픈월드를 만들지 않는다”는 문장은 “무한·무경계 월드를 만들지 않되, 서울시 지리 범위 안에서 여러 구역이 연속 연결되는 오픈월드를 단계적으로 구현한다”로 바꾼다.
3. 기존 `FlightBoundaryController`의 경계 복귀는 서울 전체 플레이 영역의 가장자리에서만 작동하도록 확장한다. 청크 경계나 행정구역 경계에서는 플레이어를 강제로 되돌리지 않는다.
4. `FREE FLIGHT`는 단일 코스 또는 소형 구역이 아니라, 서울 월드 내에서 목적지·미션을 강제하지 않는 기본 탐험 모드로 확장한다.
5. `SKYLINE RUN`과 체크포인트 코스는 오픈월드에 배치되는 선택형 활동으로 유지한다. 플레이어가 원하지 않으면 시작하지 않아도 된다.
6. TOWERGLIDE는 **비행기를 조종하는 어반 플라이트 게임**이다. 스파이더맨, 거미줄, 보행 액션, 차량 운전, 전투 시스템을 이 추가 명세에 임의로 넣지 않는다.

기존 명세와 충돌하는 코드를 수정하기 전에 먼저 현재 프로젝트를 분석하고, 변경 이유·영향 범위·롤백 방법을 `docs/DECISIONS.md`와 `WORKLOG.md`에 기록한다.

# 1. 게임 방향 — Seoul Open-World Flight

## 1.1 핵심 경험

TOWERGLIDE는 서울의 실제 지리적 특징을 참고해 만든 넓은 3D 도시를 비행기로 자유롭게 탐험하는 게임이다.

플레이어는 정해진 레이스 코스만 따라가는 것이 아니라 다음 행동을 자유롭게 선택할 수 있어야 한다.

- 한강을 따라 낮게 비행하거나 강을 가로지른다.
- 고층 빌딩 사이를 통과한다.
- 남산과 도심 스카이라인을 서로 다른 고도에서 바라본다.
- 다리, 강변, 도심 업무지구, 주거지, 저층 상권, 공원 등 서로 다른 도시 환경을 탐험한다.
- 원하는 방향으로 비행하고, 언제든 선택형 비행 도전이나 체크포인트 코스를 시작한다.
- 한 구역에서 다음 구역으로 이동할 때 별도의 로딩 화면이나 강제 텔레포트 없이 자연스럽게 이어진다.

**오픈월드의 정의:** 무한 생성 맵이 아니다. 서울시의 지리적 범위를 기반으로 여러 도시 구역이 하나의 연속된 월드처럼 연결되어 있고, 플레이어가 미션의 순서와 관계없이 자유롭게 비행할 수 있는 구조다.

## 1.2 현실감 목표

- 서울의 한강, 주요 간선도로, 교량, 산지, 공원, 고층 업무지구 등 큰 지형·도시 실루엣을 우선 살린다.
- 모든 건물을 실제 사진 수준으로 만들려 하지 않는다. 실제 위치·방향·대략적인 건물 높이와 형태를 반영하고, 창문·외벽·옥상 설비는 절차적으로 보강한다.
- 랜드마크는 일반 건물보다 높은 모델 품질을 적용하되, 라이선스가 확인된 자료 또는 직접 제작한 독립 모델만 사용한다.
- 실제 서울의 느낌을 살리되, 실시간 지도 서비스나 외부 서버에 의존하지 않고 오프라인 플레이가 가능하도록 한다.
- 시각적 사실성과 게임 플레이 가능성을 함께 고려한다. 실제 건물 배치가 너무 촘촘해 비행이 불가능하면 안전한 비행 공간을 의도적으로 확보한다.

## 1.3 범위에서 제외할 항목

첫 오픈월드 버전은 다음을 목표로 하지 않는다.

- GTA처럼 보행자 캐릭터로 도시를 걷거나 차량을 운전하는 기능
- 온라인 멀티플레이어, 실시간 유저 동기화, 서버 기반 경제 시스템
- 서울의 모든 실내 공간 구현
- 실제 건물의 모든 창문·간판·인테리어를 1:1 복제
- 무한 생성 또는 지구 전체 맵
- 유료 지도 API나 런타임 스트리밍 서비스 의존

위 기능은 별도 프로젝트 범위·성능·라이선스 검토 후 결정한다.

# 2. 서울 월드 구성 전략

## 2.1 전체 월드와 단계별 구현 범위

최종 목표는 서울의 주요 권역이 연결된 광역 월드다. 하지만 첫 버전에서 서울 전역의 상세 모델을 모두 제작하지 않는다.

다음 순서로 확장한다.

| 단계 | 월드 범위 | 목표 |
|---|---|---|
| World POC | 기존 800m × 800m 테스트 구역 | 청크 로딩/언로딩, 좌표계, LOD, 경계 검증 |
| Seoul Core | 약 2km × 2km부터 시작 | 서울다운 지형·도로·건물 밀도를 가진 실제 플레이 구역 완성 |
| Connected Districts | 인접 구역 2~4개 연결 | 구역을 넘나드는 연속 비행과 스트리밍 검증 |
| Greater Seoul | 서울 주요 권역으로 점진 확장 | 저밀도 원거리 월드 + 주요 권역의 상세 구역 구성 |

수치는 개발 시작점이다. 실제 기기 메모리·FPS·로딩 시간·기체 최고 속도를 측정해 조정한다.

## 2.2 우선 제작 권역

다음 지역을 게임 플레이 특성이 서로 다르게 느껴지는 권역으로 구성한다. 실제 지형 데이터와 도로망을 바탕으로 위치를 정하고, 임의의 좌표나 건물 높이를 실제 정보인 것처럼 표시하지 않는다.

1. **여의도·한강 권역**
   - 강과 넓은 수변 공간, 교량, 고층 업무지구를 조합한다.
   - 강을 따라 속도를 내는 장거리 비행과 교량 통과 코스를 배치한다.
2. **강남·테헤란로 권역**
   - 고층 빌딩과 넓은 간선도로, 밀집된 도심 블록을 표현한다.
   - 빌딩 사이 회피와 고도 변화 중심의 비행 구간을 배치한다.
3. **종로·광화문·남산 권역**
   - 전통·현대 건축이 섞인 도시 실루엣과 산지 지형을 표현한다.
   - 역사적 장소는 존중하되, 비행 코스와 충돌 판정을 우선 설계한다.
4. **잠실 권역**
   - 대형 랜드마크, 한강·공원·주거·상업 공간의 대비를 만든다.
   - 고층 랜드마크 주변의 상승·하강 및 원형 선회 코스를 배치한다.
5. **홍대·마포 권역**
   - 상대적으로 낮고 촘촘한 건물, 골목 형태, 상업지역 밀도를 표현한다.
   - 저고도 정밀 비행을 위한 선택형 코스를 배치한다.

한 번에 모든 권역을 제작하지 않는다. 먼저 하나의 권역을 실제로 비행 가능한 완성도까지 구현한 뒤 연결한다.

## 2.3 지형·도시 특징

월드의 지형 데이터에는 가능하면 다음 요소를 반영한다.

- 한강 본류와 주요 수변 경계
- 한강 교량과 주요 하천·수로
- 남산 및 주요 산지의 고도 변화
- 공원·녹지·운동장 등 넓은 오픈스페이스
- 주요 도로와 교차로, 철도·고가도로의 큰 구조
- 업무지구·상업지구·주거지의 건물 밀도와 높이 차이

강·산·공원은 단순한 배경 장식이 아니라 비행 경로를 결정하는 중요한 월드 요소로 취급한다.

# 3. 서울 공간 데이터·에셋 수집과 라이선스

## 3.1 반드시 지킬 원칙

1. 웹 지도 화면을 무단 캡처하거나, Google Maps·Google Earth·네이버 지도·카카오맵의 타일·3D 모델·위성사진을 추출해 게임 에셋으로 사용하지 않는다.
2. 서울시 S-Map은 서울 전역을 포함하는 3D 디지털 트윈의 **참고 자료 후보**로 조사한다. 해당 사이트에서 보이는 모델을 자동으로 다운로드·복제·변형해도 된다고 가정하지 않는다.
3. 서울시 공식 안내 페이지에는 해당 페이지 저작물의 공공누리 제4유형(출처표시·상업적 이용금지·변경금지)이 표시되어 있다. 이는 해당 페이지에 표시된 조건이며, S-Map의 각 데이터셋·3D 모델·API·이미지의 조건을 일괄적으로 확정하는 근거로 사용하지 않는다.
4. S-Map의 원본 데이터나 3D 에셋을 실제 게임에 넣기 전, 정확한 파일·데이터셋별 이용약관, 다운로드 허용 여부, 게임 내 배포 가능 여부, 수정 가능 여부, 2차 저작물 조건을 별도로 확인한다.
5. 라이선스를 확인할 수 없는 자료는 프로젝트에 넣지 않는다. 필요하면 직접 만든 프로시저럴 메시와 독립적인 랜드마크 모델로 대체한다.
6. 개인용·비상업적 프로젝트라도 저작권·라이선스 조건이 자동으로 사라지지 않는다. 공개 배포 전에 다시 검토한다.

## 3.2 데이터 소스 우선순위

다음 우선순위를 적용한다.

1. **직접 제작 데이터**: 건물 메시, 창문 패턴, 랜드마크 모델, 도로·장애물 배치.
2. **라이선스가 명확한 오픈 데이터**: 출처·라이선스·변경·재배포 조건이 확인된 도로선형, 건물 footprint, 지형 데이터.
3. **서울시·공공기관 공간정보**: 실제 게임 에셋으로 사용할 수 있는지 데이터 단위로 확인한 후 사용.
4. **OpenStreetMap(이하 OSM)**: 도로, 건물 footprint, 수역, 공원, 시설물 등의 지리적 배치 참고 및 데이터 생성에 활용 가능하다. ODbL의 출처 표시 및 파생 데이터베이스 배포 조건을 검토하고 준수한다.
5. **S-Map**: 우선 도시 형태와 시각적 특징을 확인하는 참고 자료로만 사용한다. 실제 3D 모델 또는 데이터 추출은 개별 이용 조건이 확인된 경우에만 허용한다.

## 3.3 OSM 사용 조건

OSM 데이터를 사용하는 경우 다음을 준수한다.

- OSM 데이터는 Open Database License(ODbL) 적용을 받으므로, 공개적으로 사용하는 게임에 적절한 출처 표시를 제공한다.
- 게임의 시작 화면, 설정/크레딧, 또는 적절한 인게임 위치에 `© OpenStreetMap contributors`와 라이선스 안내를 표시한다.
- 상세 안내에는 `https://www.openstreetmap.org/copyright`를 연결한다.
- OSM 데이터를 변형한 데이터베이스를 별도로 배포하는 경우 ODbL의 공유·라이선스 의무를 확인한다.
- 게임에서 보이는 시각적 산출물과 원본/가공 데이터베이스의 법적 취급은 동일하다고 단정하지 않는다. 데이터 가공·배포 구조를 기록하고, 공개 배포 전 필요한 법률 검토를 한다.
- OSM의 공용 타일 서버를 게임의 런타임 지도 서비스처럼 대량 호출하지 않는다. 가능한 경우 허용된 원본 데이터 다운로드 및 오프라인 가공 절차를 사용한다.

## 3.4 데이터 수집 전 라이선스 기록

`docs/SEOUL_WORLD_DATA_SOURCES.md`를 만들고 모든 데이터 소스마다 아래 내용을 기록한다.

- 데이터셋 이름 및 정확한 파일명
- 제공 기관·제작자
- 공식 다운로드·API·이용약관 URL
- 다운로드 날짜와 버전
- 라이선스명과 원문 링크
- 개인 이용 가능 여부
- 비상업적 공개 배포 가능 여부
- 수정·가공 가능 여부
- 게임 파일에 포함할 수 있는지 여부
- 원본 데이터 또는 파생 데이터 공개 의무
- 출처 표시 문구와 표시 위치
- 확인되지 않은 사항 및 문의 내역

**조건이 확인되지 않은 데이터는 `PENDING_REVIEW`로 표시하고 게임 빌드에 포함하지 않는다.**

# 4. 월드 좌표계와 지리 데이터 파이프라인

## 4.1 좌표계

- 지도 원본 좌표를 Unity 월드 좌표로 변환하는 단일 `WorldCoordinateSystem`을 구현한다.
- 위경도(WGS84)를 Unity 좌표에 직접 대입하지 않는다. 거리·각도·면적 계산에 적합한 투영 좌표계로 변환한 뒤 Unity 단위(meter)에 대응시킨다.
- 사용 데이터의 원본 CRS를 확인하고, 서로 다른 CRS의 데이터는 동일한 기준 좌표계로 변환한다.
- 서울 권역은 지리 좌표와 Unity 좌표 사이의 기준 원점(Origin)을 고정한다. 원점은 월드 설정 에셋에서 관리한다.
- 부동소수점 정밀도 문제를 줄이기 위해 서울 전체를 큰 절대 좌표로 배치하지 않는다. 플레이어 주변을 기준으로 한 로컬 좌표 또는 floating-origin 전략을 검토한다.
- 월드 저장·로그·데이터 파일에는 원본 지리 좌표와 Unity 로컬 좌표를 혼동하지 않도록 명시한다.

## 4.2 오프라인 데이터 가공

런타임에 외부 지도를 호출해 도시를 만드는 방식은 사용하지 않는다. 개발 단계에서 데이터를 내려받고 로컬에서 가공해 게임용 청크 데이터를 생성한다.

파이프라인:

1. 원본 데이터 확보 및 라이선스 확인
2. 좌표계·단위·데이터 범위 검증
3. 서울 월드 경계로 클리핑
4. 도로·건물·수역·공원·랜드마크 데이터 분리
5. 건물 footprint 정리 및 유효성 검사
6. 가능한 경우 건물 높이 데이터 연결
7. 높이가 없는 건물은 지역 유형에 맞는 절차적 높이 규칙으로 대체
8. 청크 단위로 분할
9. LOD용 메시와 충돌 메시 생성
10. Unity에서 불러올 수 있는 로컬 에셋/데이터로 내보내기
11. 라이선스 보고서와 데이터 출처를 함께 생성

원본 데이터가 없거나 접근이 안 되는 상황에서 임의로 실제 서울 데이터가 확보됐다고 보고하지 않는다. 이 경우 테스트용 가상 데이터로 파이프라인만 검증하고 실제 데이터 미연결 상태를 명시한다.

## 4.3 건물 모델 생성

- 실제 건물 footprint와 위치를 활용할 수 있는 데이터가 있으면 건물 배치의 기반으로 사용한다.
- 건물 높이는 신뢰할 수 있는 높이 데이터가 있을 때만 해당 값을 적용한다. 데이터가 없으면 구역별 높이 분포를 이용한 절차적 생성값으로 구분하고, 실제 높이로 오인되지 않도록 한다.
- 일반 건물은 footprint extrusion, 외벽 모듈, 창문 텍스처/셰이더, 옥상 설비 조합으로 생성한다.
- 건물마다 독립적인 수백 개 GameObject를 생성하지 않는다. 메시 결합, GPU Instancing, LOD, 공유 Material을 활용한다.
- 충돌은 단순화된 BoxCollider 또는 복수의 간단한 collider로 구성한다. 모든 창문이나 장식물에 복잡한 MeshCollider를 두지 않는다.
- 고층 빌딩·교량 등 중요한 랜드마크만 별도 상세 메시로 제작한다.
- 실제 기업 로고, 상호, 광고판, 브랜드 간판을 무단 복제하지 않는다. 필요하면 가상의 상호와 텍스처를 사용한다.

## 4.4 랜드마크

- 서울을 알아볼 수 있게 하는 랜드마크는 최소한의 고품질 수작업 모델로 표현한다.
- 랜드마크의 위치·대략적인 실루엣은 검증된 지리 자료를 사용한다.
- 사진·3D 스캔·BIM·실제 건물 모델은 라이선스 및 사용 허가를 확인하기 전까지 사용하지 않는다.
- 랜드마크 모델은 게임 내 원근과 플레이어 비행 속도에 맞춰 성능 중심으로 최적화한다.
- 실제 구조물과 완전히 동일하지 않으면 내부 제작용 가상화 모델임을 문서화한다.

# 5. 진짜 오픈월드 — 청크 스트리밍 구조

## 5.1 기본 구조

서울 월드를 하나의 거대한 Scene으로 만들지 않는다. 월드를 일정한 크기의 청크(Chunk)로 나누고, 플레이어 주변과 진행 방향에 필요한 청크만 비동기 로드한다.

- 초기 청크 크기 후보: 250m × 250m 또는 500m × 500m.
- 실제 크기는 건물 밀도, 로딩 시간, 비행 최고 속도, 메모리 사용량을 측정해 결정한다.
- 각 청크는 지형·건물·도로·장애물·랜드마크·환경 오브젝트를 독립적으로 관리한다.
- 청크 경계에는 눈에 띄는 빈 공간, 도로 끊김, 강 단절, 건물 중복이 발생하지 않아야 한다.
- 플레이어가 청크 경계를 지날 때 로딩 화면이나 텔레포트를 노출하지 않는다.

## 5.2 스트리밍 정책

`WorldStreamingManager`를 중심으로 구현한다.

- 플레이어 현재 위치와 이동 방향, 속도, 부스트 상태를 기준으로 로드 우선순위를 계산한다.
- 현재 청크와 인접 청크를 우선 로드한다.
- 일반 이동 방향 앞쪽의 청크를 뒤쪽보다 먼저 프리로드한다.
- 비행 속도가 높을수록 미리 로드해야 하는 거리와 청크 수를 늘린다.
- 화면에 보이는 원거리 월드는 낮은 LOD 또는 skyline impostor로 유지해 갑자기 도시가 사라지지 않게 한다.
- 일정 거리 이상 멀어진 청크는 안전 조건을 확인한 다음 비동기 언로드한다.
- 청크가 로드 중이거나 언로드 중인 동안 같은 요청이 중복 실행되지 않게 상태를 관리한다.
- 메모리 예산에 도달하면 플레이어 가까운 청크를 우선하고, 불필요한 먼 청크부터 정리한다.
- 비행 중 로드 실패가 발생해도 게임이 멈추거나 플레이어가 추락하지 않도록 fallback 청크를 둔다.

## 5.3 로딩 기술

- 초기 구현은 Unity `SceneManager.LoadSceneAsync`의 Additive 로드와 `UnloadSceneAsync`를 우선 검토한다.
- 청크가 많아지고 콘텐츠 빌드 파이프라인이 필요해지면 Addressables 등 Unity 공식 패키지를 검토한다.
- 도입 전 Unity 6.3 LTS와의 호환성, 빌드 크기, 메모리, 패키지 라이선스를 확인한다.
- 유료 외부 스트리밍 솔루션을 사용자 승인 없이 추가하지 않는다.
- 청크 로딩/언로딩은 메인 스레드를 장시간 점유하지 않도록 비동기 처리한다.
- 메시 생성 등 작업을 Job System/Burst로 이전할 때는 실제 병목을 프로파일링한 뒤 도입한다.

## 5.4 LOD 및 원거리 월드

거리별 상세도는 초기값으로만 사용하며 실제 시야·카메라·기체 고도에 맞춰 튜닝한다.

| 단계 | 예시 거리 | 표현 |
|---|---:|---|
| LOD0 | 0~250m | 외벽 일부 디테일, 옥상 구조, 상세 충돌 |
| LOD1 | 250~700m | 단순화된 외벽, 창문 패턴 축소, 간소 충돌 또는 충돌 생략 |
| LOD2 | 700~1,500m | 낮은 폴리곤 건물, 공유 머티리얼, 큰 형태 중심 |
| Skyline | 1,500m 이상 | 원거리 실루엣, impostor 또는 단순 메시 |

- 거리만으로 LOD를 선택하지 말고 화면 점유율과 비행 고도를 함께 고려한다.
- 청크 바깥의 원거리 도시 실루엣은 항상 일정 수준으로 유지한다.
- LOD 전환 시 팝인과 건물 깜빡임을 최소화한다.
- 플레이어 진행 방향에 맞춰 근거리 청크가 준비되기 전까지 원거리 LOD를 유지하는 parent-stays-visible 방식을 적용할 수 있다.

## 5.5 월드 경계

- 서울 전체 월드의 경계는 존재하지만, 청크 경계는 게임 경계가 아니다.
- 행정 경계나 구현되지 않은 구역을 통과할 때 갑자기 벽에 부딪히는 느낌을 만들지 않는다.
- 미구현 권역은 낮은 상세도의 도시 실루엣, 산지, 안개, 강/외곽 지형 등으로 자연스럽게 연결한다.
- 서울 월드의 외곽에 도달하면 HUD 안내, 점진적 속도 제한, 자연 지형, 안전한 회항 안내 등을 활용한다.
- 강제 복귀는 최후의 안전 장치로만 사용한다.

# 6. 비행기 게임에 맞는 도시 설계

## 6.1 비행 공간과 충돌 검증

- 실제 건물 데이터를 사용해도 모든 공간을 비행 가능하다고 가정하지 않는다.
- 도시 생성 후 비행기 크기, 회전 반경, 최대 속도를 기준으로 비행 가능 공간을 검사한다.
- 고층 건물 사이에 완전히 막힌 막다른 통로만 반복하지 않는다.
- 선택 가능한 비행 경로가 최소 2개 이상 존재하는 구역을 우선 설계한다.
- 교량·케이블·안테나처럼 충돌 위험이 큰 구조물은 시각적으로 충분히 식별되도록 한다.
- 일반 건물의 충돌체는 실제 외형과 일치하지 않아도 되지만, 플레이어가 납득할 수 있는 범위 안에 배치한다.
- 월드 생성 후 자동 검사와 수동 비행 테스트를 모두 수행한다.

## 6.2 도시 활동

오픈월드의 재미를 보완하는 선택형 활동을 배치한다.

- Skyline Run: 기존 링 체크포인트 레이스
- Landmark Circuit: 랜드마크 주변 선회/통과 코스
- Bridge Crossing: 교량 상·하부 또는 지정 게이트 통과
- Canyon Flight: 고층 건물 사이 저고도 통과
- Altitude Challenge: 지정 고도에 도달한 뒤 복귀
- Free Exploration: 미션 없이 자유 비행

활동은 오픈월드를 제한하는 필수 퀘스트가 아니라, 플레이어가 원할 때 시작하는 선택 콘텐츠다.

## 6.3 공중 교통과 움직이는 오브젝트

- 차량, 열차, 드론, 항공 장애물은 월드 전체에 대량 배치하지 않는다.
- 화면 근처나 지정된 활동 구역에서 필요한 수량만 활성화한다.
- 움직이는 오브젝트는 Object Pooling을 사용한다.
- 비행기 충돌을 유발하는 동적 오브젝트는 충분히 예측 가능해야 한다.
- 시민·차량 시뮬레이션은 첫 오픈월드 MVP의 필수 요구사항이 아니다.

# 7. 모바일 성능 및 메모리 예산

오픈월드라고 해서 모든 청크와 고해상도 모델을 메모리에 올리지 않는다.

## 7.1 기본 목표

- 기존 명세의 중급 Android 기기 30 FPS 이상 목표를 유지한다.
- 상위 기기는 60 FPS를 목표로 하되 실측 결과로 보고한다.
- 장시간 비행 중 GC Alloc, 메모리 증가, 발열, 프레임 스파이크를 측정한다.
- 구역 이동 중 로딩으로 인한 프레임 급락을 최소화한다.
- 저사양 기기에서는 LOD 거리, 그림자, 원거리 오브젝트 수를 자동으로 낮출 수 있어야 한다.

## 7.2 반드시 적용할 최적화

- GPU Instancing, 공유 Material, 메시 결합, LODGroup
- 청크·장애물·파티클 Object Pooling
- 원거리 건물의 단순 메시 또는 impostor
- 가까운 건물에만 상세 충돌체 적용
- 청크별 오브젝트 수와 메모리 사용량 제한
- 비동기 로딩 및 언로딩
- 사용하지 않는 텍스처·메시 참조 해제
- 불필요한 실시간 그림자·반사·투명 효과 제한
- 로드 우선순위 및 동시 로딩 수 제한

## 7.3 프로파일링 필수 항목

`docs/SEOUL_WORLD_PERFORMANCE.md`에 아래 항목을 기록한다.

- 테스트 기기 모델, RAM, GPU, OS, 화면 해상도
- 청크 크기와 동시에 로드된 청크 수
- LOD별 오브젝트/메시 수
- 현재/최대 메모리
- 청크 로드·언로드 시간
- 최대 속도 및 부스트 상태에서의 프레임 시간
- 30 FPS 미만 구간과 원인
- 장시간 비행 테스트의 발열·메모리 변화

측정하지 않은 FPS나 로딩 시간을 성공 수치로 보고하지 않는다.

# 8. UI 추가 요구사항

기존 HUD를 유지하면서 오픈월드 탐험에 필요한 최소 UI를 추가한다.

- **World Map:** 현재 위치, 주요 권역, 랜드마크, 선택 활동 표시
- **Compass:** 현재 비행 방향 및 주요 목적지 방향 표시
- **District Label:** 권역에 진입하면 지역명 안내
- **Nearby Landmark:** 주변 랜드마크 이름과 대략적인 거리 표시
- **Streaming Debug (개발용):** 현재 청크 ID, 로딩 상태, LOD, 메모리 사용량 표시
- **Map/Data Credits:** OSM 등 외부 데이터 출처와 라이선스 표시

월드 지도는 전체 월드를 세밀한 실시간 3D 렌더링으로 다시 그리지 않는다. 2D 간략 지도 또는 미리 생성된 정적 데이터 기반으로 구현한다.

### 책임 정의

- `WorldCoordinateSystem`: 지리 좌표와 Unity 월드 좌표 간 변환을 단일 책임으로 관리한다.
- `SeoulWorldDefinition`: 월드 원점, 월드 범위, CRS, 청크 크기, 초기 권역 정의를 가진다.
- `SeoulDistrictDefinition`: 권역 경계, 명칭, 테마, 대표 랜드마크, 기본 LOD 정책을 가진다.
- `WorldChunkId`: 청크의 고유 X/Z 인덱스 또는 안정적인 ID를 관리한다.
- `WorldChunkCatalog`: 청크 데이터/씬/에셋의 위치를 조회한다.
- `WorldStreamingManager`: 플레이어 위치·속도·방향에 따라 로드/언로드 우선순위를 결정한다.
- `WorldChunkLoader`: 비동기 청크 로드/언로드를 실행하고 중복 요청을 막는다.
- `WorldChunkState`: Unloaded, Loading, Loaded, Unloading, Failed 상태를 관리한다.
- `WorldLodController`: 거리·시야·고도에 맞춰 LOD를 제어한다.
- `SkylineImpostorController`: 원거리 도시의 실루엣을 유지한다.
- `BuildingMeshGenerator`: 검증된 footprint·높이 속성으로 절차적 건물 메시를 생성한다.
- `TerrainHeightSampler`: 지형 고도 조회와 지형 메시 생성에 필요한 데이터를 제공한다.
- `LandmarkRegistry`: 권역별 랜드마크의 위치·표시명·표시 조건을 관리한다.
- `SeoulWorldBoundaryController`: 서울 월드 외곽의 자연스러운 경계만 처리한다.
- `SeoulWorldValidator`: 청크 누락, 겹침, 잘못된 좌표, 건물 높이/충돌 이상을 검사한다.
- `SeoulWorldLicenseReportBuilder`: 사용 데이터 출처 및 라이선스 기록을 취합한다.

기존 Phase 0~5를 무시하고 대규모 도시를 한 번에 만들지 않는다. 기존 Phase 1의 Flight Feel POC를 유지하고, 오픈월드 기능은 별도 후속 단계로 추가한다.

## Phase OW0 — 데이터·라이선스 조사 및 설계

작업:

- 현재 프로젝트의 Unity 버전, 씬, 도시 생성 구조 분석
- 사용 가능한 공개 공간 데이터 후보 조사
- OSM·서울시 데이터·S-Map 각각의 정확한 이용 조건 기록
- 좌표계 및 서울 월드 원점 설계
- 초기 서울 테스트 권역 선정
- 청크 크기·LOD·메모리 예산 초안 작성

완료 조건:

- `docs/SEOUL_WORLD_DATA_SOURCES.md` 작성
- 라이선스 미확인 데이터를 빌드에 넣지 않도록 절차 마련

- 기존 비행 시스템에 미치는 영향 분석

## Phase OW1 — World Streaming POC

목표: 실제 서울 모델이 없어도 청크 스트리밍 구조가 동작하는지 검증한다.

작업:

- 기존 800m × 800m 테스트 월드를 여러 청크로 분할
- 테스트용 절차적 건물과 도로를 청크별로 배치

- 청크 경계에서 건물·도로·지형이 끊기지 않는지 검사

완료 조건:

- 비행 중 청크 전환이 정상 동작
- 청크 로드/언로드 중 게임 진행이 멈추지 않음
- 최대 속도 + 부스트 조건에서 앞쪽 청크가 제때 준비됨
- 누락 청크나 중복 로드가 발생하지 않음
- 메모리 사용량이 기록됨

## Phase OW2 — Seoul Core 데이터 임포트

목표: 검증된 공간 데이터를 이용해 서울의 한 권역을 실제 비행 가능한 월드로 만든다.

작업:

- 권역별 도로·건물 footprint·수역·공원·지형 자료 임포트
- 높이 데이터가 있는 건물과 없는 건물 분리
- 건물 높이와 LOD 생성
- 랜드마크 1~3개 우선 구현
- 지형·도로·한강 등 큰 형태 검수
- 라이선스·출처 메타데이터 보존

완료 조건:

- 선택한 권역의 주요 도로·건물 밀도·수역·고도 특성이 식별 가능
- 건물·도로가 좌표상 크게 어긋나지 않음
- 비행 가능한 통로 확보
- 모든 사용 데이터의 라이선스가 기록됨

## Phase OW3 — Connected Districts

목표: 인접한 여러 권역을 로딩 화면 없이 연결한다.

작업:

- 권역별 청크 카탈로그 확장
- 원거리 Skyline 연결
- 권역 진입 UI와 지도 표시
- 청크 프리로드 방향/속도 계산 개선
- 월드 바깥 경계 처리

완료 조건:

- 최소 2개 이상의 권역을 연속 비행 가능
- 권역 경계에서 로딩 화면/강제 텔레포트 없음
- 이동 방향에 맞춰 청크가 미리 준비됨
- 청크 전환 중 심각한 프레임 드랍이나 메모리 누수 없음

## Phase OW4 — Open-World Activities & Polish

작업:

- 자유 비행 목적지 및 선택형 챌린지 배치
- 월드 지도·나침반·랜드마크 UI
- 구역별 분위기·환경음·시간대 표현
- 주요 권역의 건물·지형 디테일 보강
- 성능 프로파일링과 저사양 옵션 튜닝

완료 조건:

- 미션을 시작하지 않아도 자유롭게 비행 가능
- 주요 활동은 월드 어디에서든 접근 가능
- 안드로이드 실기기 성능 측정 기록 완료

## Phase OW5 — 서울 권역 확대

- 새로운 권역은 기존 청크·좌표·LOD·라이선스 파이프라인으로 추가한다.

# 14. 비행기 선택 및 기종별 비행 시스템 (Aircraft Selection & Flight Profiles)

## 14.1 목표

TOWERGLIDE는 한 종류의 비행기만 조종하는 게임이 아니라, 플레이어가 격납고(HANGAR)에서 여러 종류의 항공기를 선택하고 같은 서울 오픈월드를 서로 다른 조작감으로 탐험하는 게임으로 확장한다.

**필수 방향:**

- 소형 프로펠러기, 곡예기, 여객기, 전투기 등 외형과 비행 특성이 뚜렷하게 다른 기체를 선택할 수 있어야 한다.
- 단순히 모델과 색상만 바뀌는 스킨 시스템으로 구현하지 않는다.
- 기체마다 질량, 크기, 관성, 추력, 양력, 항력, 최고 속도, 상승력, 선회 반응, 감속 성능이 다르게 느껴져야 한다.
- 기존 `AircraftFlightController`를 기종마다 복사하지 않는다. 공통 물리 컨트롤러와 기종별 `AircraftFlightTuning` 데이터로 구현한다.
- 모든 기체는 기본 FREE FLIGHT를 플레이할 수 있어야 한다. 다만 기체 크기와 성능에 맞지 않는 좁은 통과 코스를 강제하지 않는다.
- 첫 버전에서 모든 항공기를 완성하려 하지 않는다. 최소 3종을 실제 선택·비행 가능하게 만든 뒤 나머지 기종을 확장한다.

## 14.2 기체 카테고리

다음 기종을 장기적인 기본 라인업으로 설계한다. 실제 제조사·기체의 상표, 로고, 고유 도장, 3D 모델을 복제하지 말고 독자적인 디자인과 가상의 기체명을 사용한다.

| 카테고리 | 예시 가상 기체 | 외형 및 플레이 특성 | 우선순위 |
|---|---|---|---|
| 소형 단발 프로펠러기 | Scout P-1 | 작고 가벼움, 저속 조종이 쉬움, 좁은 공간 탐험에 적합 | MVP |
| 곡예 비행기 | Aero S-2 | 롤·피치 반응이 빠르고 기동성이 높음, 정밀 비행과 곡예에 적합 | MVP |
| 전투기형 제트 | Viper F-9 | 높은 추력과 최고 속도, 빠른 상승 및 고속 선회, 속도 관리가 중요 | MVP |
| 지역 여객기 | Metro 70 | 중형 동체, 쌍발 터보프롭 또는 소형 제트 실루엣, 안정적인 순항 | 후속 1차 |
| 중·단거리 여객기 | Cityliner 180 | 큰 동체와 날개, 높은 질량과 관성, 넓은 선회 반경 및 긴 감속 거리 | 후속 1차 |
| 대형 장거리 여객기 | Longhaul 300 | 매우 큰 동체와 날개, 높은 관성, 넓은 비행 공간과 완만한 기동 필요 | 후속 2차 |
| 화물기 | CargoLift 220 | 여객기와 다른 동체·날개 실루엣, 무거운 기체와 완만한 반응 | 후속 2차 |

위 기체명은 작업용 가상 이름이다. 실제 항공기 제조사의 모델명이나 상표로 오인되지 않도록 최종 명칭과 외형을 독립적으로 정한다.

### MVP에서 실제 구현할 최소 라인업

첫 기체 선택 기능 검증에는 다음 3종을 우선 구현한다.

1. **소형 프로펠러기:** 저속·저고도 탐험 기준 기체.
2. **전투기형 제트:** 고속·고추력 기준 기체.
3. **중형 여객기:** 대형 동체·높은 관성·넓은 회전 반경 기준 기체.

곡예 비행기는 소형 프로펠러기의 기본 물리 구조를 확장해 추가하고, 지역 여객기·대형 여객기·화물기는 이후 단계에서 모델과 물리 데이터를 분리해 추가한다.

## 14.3 기종별 비행 특성

기종별 특성은 실제 항공기 성능표를 그대로 구현하려는 목적이 아니라, 게임에서 서로 구분되는 조작 경험을 만들기 위한 아케이드 기반의 세미 리얼리스틱 모델이다. 실제 항공기 제원처럼 보이는 수치를 임의로 단정하지 않는다. 게임 밸런스 수치는 `AircraftFlightTuning` 데이터에 별도로 기록하고 UI에도 필요하면 '게임 내 성능'임을 표시한다.

### 소형 프로펠러기

- 가벼운 질량과 비교적 낮은 속도를 기본으로 한다.
- 저속에서도 비교적 안정적으로 조종할 수 있어야 한다.
- 좁은 건물 사이와 강변 저고도 탐험에 적합하다.
- 큰 추력보다 조종 반응과 시야 확보를 우선한다.
- 급격한 입력 시 기체가 과도하게 뒤집히지 않도록 초보자 보조를 제공한다.

### 곡예 비행기

- 소형 프로펠러기보다 롤·피치 회전 반응이 빠르다.
- 롤, 루프 등 곡예 동작을 수행할 수 있는 기체 제어 프리셋을 제공한다.
- 곡예 동작을 Transform 강제 회전으로 처리하지 않는다. Rigidbody 토크와 속도·고도 조건에 기반해 표현한다.
- 곡예 모드는 일반 FREE FLIGHT와 별도의 연습 미션으로 확장할 수 있다.

### 전투기형 제트

- 높은 추력과 높은 최고 속도를 제공한다.
- 고속에서 조종 입력이 지나치게 민감해지지 않도록 속도별 조종 권한을 조절한다.
- 소형 기체보다 높은 속도를 낼 수 있지만, 고속 상태에서는 선회 반경과 감속 거리가 커지는 느낌을 준다.
- Boost를 기본 상시 기능으로 만들지 않는다. 엔진 추력과 Boost를 구분하고 부스트는 게임 밸런스에 맞게 제한한다.
- 공중전·미사일·무기 시스템은 이번 기체 선택 기능에 포함하지 않는다. 전투기 외형과 비행 특성만 우선 구현한다.

### 여객기

- 동체·날개·꼬리날개가 소형기보다 크고 무거운 실루엣이어야 한다.
- 큰 질량과 관성, 높은 안정성, 느린 롤 반응, 넓은 선회 반경을 표현한다.
- 속도를 줄이는 데 더 긴 시간이 걸리며 급격한 방향 전환에 불리해야 한다.
- 좁은 빌딩 통로와 소형 체크포인트를 여객기로 통과하도록 강제하지 않는다.
- 한강 상공, 외곽의 넓은 공간, 고고도 비행, 넓은 게이트, 공항 접근 코스 등 기체 크기에 맞는 활동을 제공한다.
- 여객기는 비행 중 동체가 건물에 가려질 수 있으므로 카메라 거리·FOV·충돌 여유 공간을 기체 크기에 따라 자동 조정한다.

### 화물기

- 여객기와 다른 동체 실루엣, 날개·엔진 배치 및 화물기 특유의 외형을 제공한다.
- 큰 질량과 높은 관성, 안정적인 순항을 중심으로 한다.
- 화물 운송 미션은 후속 콘텐츠로 남기고, 초기에는 FREE FLIGHT 호환성부터 구현한다.

## 14.4 공통 물리 컨트롤러와 기종별 설정 데이터

기종을 추가할 때 기존 비행 컨트롤러를 복사하거나 `if (aircraftType == ...)` 분기를 계속 늘리지 않는다.

권장 구조:

```text
Scripts/
├─ Flight/
│  ├─ AircraftFlightController.cs       # 공통 Rigidbody 물리
│  ├─ AircraftFlightTuning.cs           # ScriptableObject 기종별 튜닝 데이터
│  ├─ AircraftDefinition.cs             # 기체 ID, 이름, 분류, 프리팹, 미리보기
│  ├─ AircraftCatalog.cs                # 선택 가능한 기체 목록
│  ├─ AircraftSelectionService.cs       # 선택/현재 기체 상태 관리
│  ├─ AircraftSpawnService.cs           # 선택 기체 스폰 및 초기 상태
│  ├─ AircraftVisualController.cs       # 프로펠러/제트 엔진/조종면 연출
│  └─ AircraftCameraProfile.cs          # 기체 크기별 카메라 설정
├─ UI/
│  ├─ HangarSelectionController.cs
│  ├─ AircraftSelectionCard.cs
│  └─ AircraftPreviewController.cs
└─ Save/
   └─ AircraftUnlockSaveData.cs
```

`AircraftDefinition`에는 다음 데이터를 둔다.

- 고유 ID와 표시 이름
- 기체 카테고리
- 짧은 설명
- 3D 프리팹 및 미리보기 아이콘/이미지
- `AircraftFlightTuning` 참조
- 카메라 프로파일 참조
- 기체 크기(길이·날개폭·높이 등 게임 월드 단위)
- 기본 스폰 위치 오프셋과 초기 속도
- 잠금 여부 및 해금 조건 ID
- 지원하는 활동/코스 태그(예: `TIGHT_ROUTE`, `HIGH_SPEED`, `WIDE_AIRSPACE`, `AEROBATICS`)

`AircraftFlightTuning`에는 최소 다음 값을 포함한다.

- Rigidbody 질량과 관성 텐서 설정값
- 엔진 추력 및 추력 반응 속도
- 기본 양력 및 속도별 양력 계수
- 항력 및 고속 항력 계수
- Pitch/Roll/Yaw 토크와 각 축의 응답 곡선
- 각속도 감쇠와 안정화 보조력
- 최소 유효 속도와 실속 보조 파라미터
- 일반 최고 속도 및 속도 제한 보조값
- 최대 상승력/하강 반응
- Air Brake 효율과 감속 반응
- Boost 사용 가능 여부, 출력, 지속시간 및 쿨다운
- 기체 크기에 따른 충돌 여유 및 복귀 위치 오프셋

주의:

- 질량만 바꾸고 추력·양력·항력·관성을 보정하지 않아 기체가 비현실적으로 움직이는 상태를 방치하지 않는다.
- 비행 물리 단위는 기존 프로젝트의 `1 Unity unit ≈ 1m` 기준과 일치시킨다.
- 기종별 설정은 ScriptableObject 에셋으로 저장하고 코드 상수로 하드코딩하지 않는다.
- 공통 입력 상태(Pitch/Roll/Yaw/Throttle/Boost/Air Brake)는 유지한다. 기종별 조작 UI를 별도 구현하지 않는다.
- 새 기체를 추가할 때는 데이터 에셋과 프리팹을 등록하는 방식으로 확장할 수 있어야 한다.

## 14.5 격납고(HANGAR) 및 기체 선택 UI

기존 메인 메뉴의 `HANGAR` 항목을 실제 기체 선택 화면으로 확장한다.

화면 구성:

- 중앙: 선택된 비행기의 3D 미리보기. 천천히 회전하거나 사용자가 드래그해 관찰할 수 있다.
- 상단: 기체 이름, 분류, 짧은 특징 설명.
- 좌우 또는 하단: 기체 선택 카드 목록. 모바일 가로 화면에서 터치하기 쉬운 크기로 배치한다.
- 성능 영역: 속도, 가속, 기동성, 안정성, 크기 항목을 막대 또는 간단한 비교 지표로 표시한다.
- 하단 주요 버튼: `SELECT` / `FLY` 또는 `선택` / `비행 시작`.
- 잠긴 기체는 잠금 상태와 해금 조건을 표시하되, 결제를 유도하지 않는다.
- 기체 선택 화면을 열었을 때 현재 선택 기체가 명확히 표시되어야 한다.

성능 지표 정책:

- UI의 별점·막대는 실제 항공기 인증 제원이 아니라 게임 내 상대 성능이다.
- 숫자를 표시하면 게임 내 밸런스 수치임을 명시한다.
- 서로 다른 단위나 조건의 수치를 억지로 단일 점수로 환산하지 않는다.
- 속도만 높은 기체가 무조건 좋은 기체처럼 보이지 않도록 기동성·안정성·크기·감속 능력을 함께 표시한다.

## 14.6 기체 선택·저장·해금 규칙

- 선택한 기체 ID는 로컬 저장 데이터에 저장한다.
- 앱을 재실행해도 마지막 선택 기체가 유지되어야 한다.
- 세이브 데이터에 버전 필드를 두고 기체 목록이 추가되어도 기존 데이터가 깨지지 않게 한다.
- 처음부터 최소 3종(소형 프로펠러기, 전투기형 제트, 중형 여객기)을 선택 가능하게 하거나, 구현이 단계적으로 진행된다면 미구현 기체는 목록에서 비활성/개발 예정으로 분리한다.
- 잠금 해금 방식은 비행 거리, 비행 시간, 챌린지 완주 등 로컬 플레이 기록을 우선 사용한다.
- 광고, 인앱 결제, 계정, 서버를 추가하지 않는다.
- 기체 선택은 비행 시작 전에 수행한다. 공중에서 기체를 즉시 교체하는 기능은 구현하지 않는다.
- 공항·격납고에서 착륙 후 기체를 변경하는 기능은 후속 확장으로 설계할 수 있다.

## 14.7 기체 크기에 따른 월드·코스 호환성

오픈월드의 모든 공간이 모든 기체에 적합하다고 가정하지 않는다.

- 소형 프로펠러기와 곡예기는 좁은 도심 비행 코스 및 저고도 정밀 통과에 적합하다.
- 전투기형 제트는 고속·고고도·넓은 회전 공간을 갖춘 코스에 적합하다.
- 지역 여객기와 중형 여객기는 한강·외곽·넓은 도로축·고고도 등 넓은 비행 공간을 이용한다.
- 대형 여객기와 화물기는 별도의 넓은 회랑과 충분한 선회 반경을 확보한다.
- 여객기나 대형 기체에 소형기 전용 링 코스를 강제로 제공하지 않는다.
- 같은 챌린지에 여러 기종이 참여하는 경우 기체별 통과 판정 크기, 속도, 시간 제한을 별도로 밸런싱한다.
- 기체 크기에 맞춘 안전 거리와 카메라 거리를 적용한다. 카메라가 건물 안으로 들어가거나 기체가 화면 밖으로 사라지지 않도록 한다.
- 대형 기체가 건물 또는 교량을 통과할 수 없는 물리적 상황을 무리하게 보정해 건물 안으로 통과시키지 않는다.

### 활주로·이착륙 범위

기존 MVP는 공중 스폰 방식으로 유지해 기체 선택 시스템을 먼저 검증한다. 단, 여객기를 자연스럽게 조종하는 경험을 위해 다음 단계에서 활주로·이륙·착륙을 추가할 수 있도록 구조를 열어 둔다.

후속 구현 시:

- 모든 기체를 즉시 이륙 가능한 상태로 스폰하는 방식과 활주로에서 시작하는 방식을 게임 모드/옵션으로 분리한다.
- 여객기와 대형 화물기는 충분한 활주 거리와 넓은 회전·착륙 공간이 필요하다.
- 소형 프로펠러기는 짧은 활주 구간 또는 간이 비행장에서 시작할 수 있다.
- 착륙 판정은 속도·하강률·기체 자세·활주로 접촉 상태를 함께 확인한다.
- 첫 구현에서는 실제 항공 관제·공항 운항 절차를 시뮬레이션하지 않는다.
- 실제 공항의 활주로 배치·표지·로고·항공사 도장을 무단으로 복제하지 않고, 라이선스가 명확한 데이터 또는 독자적인 가상 비행장을 사용한다.

## 14.8 카메라·사운드·시각 효과 차별화

- 기체 길이와 날개폭에 따라 추적 카메라 거리, 높이, FOV, 카메라 충돌 반경을 조절한다.
- 소형 프로펠러기는 프로펠러 회전과 엔진 진동을 표현한다.
- 제트 전투기와 여객기는 엔진 팬/배기 표현과 속도에 따른 사운드를 구분한다.
- 여객기와 화물기는 엔진 사운드를 기체 크기에 맞춰 더 낮고 묵직하게 설계할 수 있다.
- 기체별 사운드와 VFX는 별도 프리팹/프로파일로 관리한다.
- 실제 항공기 제조사 또는 항공사의 상표·로고·독점 디자인을 무단 사용하지 않는다.
- 모바일 성능을 위해 엔진 효과, 파티클, 실시간 조명을 제한하고 LOD를 적용한다.

## 14.9 에셋·라이선스·비상업적 이용

- 무료 에셋이라고 해서 저작권이 없는 것은 아니다. 각 항공기 모델·텍스처·사운드의 정확한 라이선스를 확인한다.
- CC0, 퍼블릭 도메인 또는 게임 내 사용·수정·배포 조건이 명확한 무료 에셋을 우선한다.
- CC BY 계열 에셋은 저작자 표시 및 라이선스 조건을 지킨다.
- CC BY-NC는 비상업적 이용 조건을 확인하고, 공개 배포와 플랫폼 약관이 해당 조건에 부합하는지 별도로 검토한다.
- 실제 항공기 제조사 로고, 항공사 도장, 군용 부대 마크, 게임/영화에서 추출한 모델을 무단 사용하지 않는다.
- 실제 기종을 참고하더라도 기체 실루엣·도장·이름·계기판은 독립적인 가상 디자인으로 제작하는 방안을 우선한다.
- 에셋마다 `docs/THIRD_PARTY_ASSETS.md`에 제작자, 원본 URL, 라이선스, 수정 허용, 게임 포함 허용, 출처 표시를 기록한다.
- 라이선스 확인이 끝나지 않은 기체는 회색 박스/프로시저럴 임시 모델로 대체한다.

## 14.10 추가 클래스 및 데이터

권장 클래스:

- `AircraftDefinition`: 기체 메타데이터와 프리팹 참조
- `AircraftCatalog`: 전체 기체 목록 및 ID 조회
- `AircraftSelectionService`: 현재 선택 기체 상태
- `AircraftSpawnService`: 선택 기체 스폰과 초기화
- `AircraftFlightTuning`: 기종별 비행 물리 설정
- `AircraftCameraProfile`: 기체별 카메라 설정
- `AircraftVisualProfile`: 엔진·프로펠러·조종면 시각 효과
- `HangarSelectionController`: 격납고 UI 제어
- `AircraftPreviewController`: 3D 미리보기 회전/선택
- `AircraftUnlockSaveData`: 로컬 해금 상태 및 마지막 선택값

기존 코드베이스의 네이밍 규칙과 구조가 다르면 기존 규칙을 우선한다. 위 클래스 목록을 그대로 강제로 생성하지 말고 현재 구조에 맞게 책임을 배치한다.

## 14.11 테스트 및 승인 기준

### 기능 테스트

- 기체 선택 후 정확한 프리팹이 스폰되는지
- 기체별 `AircraftFlightTuning`이 올바르게 적용되는지
- 앱 재실행 후 마지막 선택 기체가 유지되는지
- 존재하지 않는 기체 ID 또는 손상된 세이브 데이터에서 기본 기체로 복구되는지
- 미구현/잠금 기체를 선택할 수 없도록 처리하는지
- 기체 선택 후 FREE FLIGHT와 SKYLINE RUN 진입이 정상 동작하는지
- 기체별 카메라 거리·FOV·충돌 크기가 적용되는지
- 기체별 엔진·프로펠러 VFX/사운드가 잘못 연결되지 않는지

### 비행 특성 테스트

- 소형 프로펠러기가 저속에서 안정적으로 조종되는지
- 전투기형 제트가 더 높은 속도와 추력을 제공하는지
- 여객기가 더 큰 관성과 넓은 선회 반경을 보이는지
- 같은 입력을 주었을 때 기종별 움직임이 실제로 구분되는지
- 기체를 바꿔도 입력 방향·카메라 추적·충돌·복귀 기능이 깨지지 않는지
- 여객기와 대형 기체가 작은 링이나 좁은 코스에 무리하게 배치되지 않는지

### 승인 조건

- 최소 3종의 기체를 격납고에서 선택할 수 있다.
- 세 기체 모두 실제 FREE FLIGHT에서 비행 가능하다.
- 세 기체의 가속·속도·기동성·관성 차이가 플레이로 확인된다.
- 기체별 데이터가 ScriptableObject 등 데이터 중심으로 분리되어 있다.
- 기존 비행 컨트롤러의 중복 구현이 없다.
- Android 중급 기기에서 모델·카메라·이펙트 추가로 인한 성능 저하를 측정하고 기록했다.

## 14.12 구현 단계

### Phase AC0 — 기존 구조 분석

- 기존 AircraftFlightController, AircraftFlightTuning, Hangar UI, 저장 구조가 있는지 확인한다.
- 있으면 최대한 재사용하고, 없으면 현재 프로젝트 컨벤션에 맞는 최소 구조를 설계한다.
- 기존 POC의 비행 조작을 보존한다.

### Phase AC1 — 기체 선택 POC

- 소형 프로펠러기, 전투기형 제트, 중형 여객기 임시 모델 3종을 구성한다.
- ScriptableObject 기반 기체 정의와 튜닝 데이터를 만든다.
- HANGAR 화면에서 3종을 선택할 수 있게 한다.
- 선택 기체로 FREE FLIGHT에 진입하고 기체별 물리 차이를 테스트한다.
- 마지막 선택값을 로컬에 저장한다.

완료 조건: 3종 모두 선택·스폰·비행·저장/복원이 가능하고 조종감 차이가 확인된다.

### Phase AC2 — 모델·연출 고도화

- 임시 모델을 라이선스가 확인된 무료 모델 또는 직접 제작 모델로 교체한다.
- 기체별 재질, 엔진, 프로펠러, 조종면, 사운드, 카메라 튜닝을 적용한다.
- 기체별 성능 요약 UI를 완성한다.

### Phase AC3 — 라인업 확장

- 곡예 비행기, 지역 여객기, 대형 여객기, 화물기를 추가한다.
- 각 기종에 맞는 비행 코스 태그와 월드 공간을 연결한다.
- 필요한 경우 기체별 이착륙 모드를 추가한다.

### Phase AC4 — 기체별 활동과 밸런스

- 기체 분류별 챌린지와 자유 비행 목적지를 추가한다.
- 기체별 미션 점수·시간·통과 반경을 밸런싱한다.
- Android 실기기에서 모든 기체의 FPS·메모리·충돌 판정을 점검한다.

## 14.13 Claude Code 우선 실행 지시

서울 오픈월드 스트리밍 POC와 기체 선택 시스템을 한 번에 대규모로 구현하지 않는다.

1. 우선 기존 월드/비행 코드와 현재 `AircraftFlightTuning`의 유무를 확인한다.
2. 오픈월드 Phase OW0/OW1과 기체 선택 Phase AC0를 분석한다.
3. 기존 비행 조작을 유지한 상태에서 소형 프로펠러기 1종을 기준 기체로 정리한다.
4. 그다음 전투기형 제트와 중형 여객기를 별도 튜닝 데이터로 추가한다.
5. HANGAR에서 3종을 선택하고 실제 FREE FLIGHT에 진입하는 흐름을 우선 완성한다.
6. 이 단계에서 서울 전역 데이터 임포트, 상세 모델링, 이착륙, 화물 미션, 공중전은 시작하지 않는다.
7. 선택·스폰·물리·저장 테스트가 통과한 후에 서울 월드 및 기체 라인업 확장을 진행한다.

첫 결과 보고에는 다음을 포함한다.

- 기존 비행 컨트롤러 및 튜닝 구조
- 추가/수정한 기체 정의와 튜닝 데이터
- HANGAR 선택 UI 동작 여부
- 실제 선택·스폰 가능한 기체 목록
- 세 기체의 비행 특성 비교 테스트 결과
- 저장·복원 결과
- Android 성능 및 미검증 사항

**절대 금지:** 세 기체의 프리팹 외형만 바꾸고 동일한 물리값을 적용한 뒤 기체 선택 시스템이 완성됐다고 보고하지 않는다.

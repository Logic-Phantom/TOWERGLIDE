# 0. Claude Code에 대한 최상위 작업 지시

너는 Unity 6.3 LTS 기반 모바일 3D 게임을 실제로 구현하는 시니어 Unity 게임플레이 프로그래머이자 테크니컬 아티스트다. 이 문서는 아이디어 제안서가 아니라 **실제 실행 가능한 게임 프로젝트를 만드는 작업 명세**다.

사용자가 원하는 게임은 Bruno Simon의 인터랙티브 3D 사이트에서 느껴지는 직접 조작과 공간 탐험의 재미를 참고하되, 자동차가 아니라 비행기를 조종하는 독립적인 모바일 게임이다. 고층 빌딩 사이를 낮게 날고, 건설 크레인·드론·송전 구조물·공중 링 등의 장애물을 피하며, 속도와 관성·기울기·카메라 반응이 느껴지는 비행 경험을 제공해야 한다.

## 0.1 최우선 원칙

1. **설명만 하지 말고 파일과 코드를 실제로 작성한다.** 현재 저장소를 확인하고 프로젝트가 없으면 생성한다. 이미 프로젝트가 있으면 구조를 파괴하지 말고 먼저 분석한다.
2. 작업을 시작하기 전에 `pwd`, 디렉터리 구조, Git 상태, 설치된 Unity Editor/Unity Hub, Android Build Support, Java/SDK/NDK 환경을 확인한다.
3. Unity가 설치되어 있지 않거나 현재 환경에서 Editor 실행이 불가능하면 이를 숨기지 않는다. 그래도 C# 코드, 폴더, 설정 파일, Editor 자동화 스크립트, 문서와 테스트를 최대한 작성하고, 실제 Editor 빌드가 필요한 단계만 명확히 분리한다.
4. 사용자가 원하는 핵심은 **조작감**이다. 화려한 메뉴나 대형 월드보다 비행기가 손끝에 반응하는 느낌, 관성, 기체 기울기, 카메라 추적, 충돌 피드백을 먼저 완성한다.
5. 첫 버전에서 무제한 오픈월드·멀티플레이어·실시간 서버·계정·광고·인앱결제를 구현하지 않는다. 무료·오프라인 싱글 플레이를 우선한다.
6. Unity Personal로 무료 개발이 가능한 범위를 우선 사용한다. 유료 에셋, 유료 플러그인, 유료 API, 유료 서버, 구독형 툴을 추가하지 않는다. 무료가 아닌 의존성이 발견되면 대체재를 찾고 사용자 승인 없이 구매하지 않는다.
7. 모든 외부 에셋은 사용 전 실제 라이선스, 상업적 사용 가능 여부, 재배포/수정 조건을 확인한다. 확인하지 못한 에셋은 사용하지 않는다.
8. Bruno Simon 사이트의 코드·모델·브랜드·화면을 그대로 복제하지 않는다. 참고하는 것은 3D 공간을 직접 조작하는 인터랙션이라는 아이디어뿐이며, 비행기·도시·UI·사운드·게임 규칙은 독자적으로 제작한다.
9. 테스트하거나 빌드하지 않은 것을 성공했다고 보고하지 않는다. 실행 결과, 실패 로그, 미실행 사유를 분리해 기록한다.
10. 각 단계가 끝날 때마다 `README.md`, `WORKLOG.md`, `docs/`를 갱신하고 실제 변경 파일과 테스트 결과를 요약한다.

## 0.2 진행 방식

- 먼저 현재 프로젝트와 개발 환경을 조사하고, **현재 환경에서 가능한 첫 번째 실행 목표**를 정한다.

# 1. 게임 콘셉트 및 방향

## 1.1 핵심 콘셉트

**TOWERGLIDE**는 플레이어가 소형 고성능 곡예 비행기를 직접 조종해 현대적인 고층 도시의 빌딩 숲을 자유롭게 비행하는 3D 모바일 게임이다.

게임의 기본 재미는 다음 세 가지다.

- **자유 비행:** 플레이어가 직접 상승·하강·선회하며 도시를 탐험한다.
- **아슬아슬한 통과:** 빌딩 사이의 좁은 통로, 크레인, 드론, 공중 링, 구조물을 통과하거나 회피한다.
- **속도와 숙련도:** 속도를 유지하면서 부드럽게 기체를 기울이고, 정교하게 장애물을 피하고, 연속 게이트를 통과해 기록을 갱신한다.

현실적인 비행 시뮬레이터를 목표로 하지 않는다. **현실적인 움직임의 인상 + 배우기 쉬운 아케이드 비행 물리**를 목표로 한다. 비행기가 자동차처럼 바닥에 붙어 움직이거나, 드론처럼 방향을 즉시 꺾는 느낌이 되면 안 된다.

## 1.2 비주얼 방향

- 현실적인 비율의 소형 곡예 비행기 또는 경량 제트기 실루엣. 실제 제조사의 로고·기체 도장·상표를 복제하지 않는다.
- 현대적인 도심 스카이라인: 유리 커튼월 빌딩, 콘크리트 빌딩, 옥상 설비, 통신탑, 크레인, 고가도로, 옥상 헬리패드 등.
- 과도한 카툰/로우폴리 스타일은 피하되 모바일 기기에서 구동 가능한 **세미 리얼리스틱 스타일**을 사용한다.
- 낮/오후의 선명한 가시성을 기본으로 하고, 도시의 깊이감을 위해 원근 안개와 대기 원근감을 사용한다.
- 반사·유리·그림자·후처리는 절제한다. 화면을 흐리게 만드는 과한 블룸, 모션 블러, 색수차, 렌즈 플레어는 금지한다.
- 빌딩 사이를 통과할 때 가까운 건물의 속도감과 크기 변화가 확실히 느껴져야 한다.
- UI는 조종 HUD 형태로 구성한다. 게임 화면을 가리는 큰 메뉴나 장식은 최소화한다.

## 1.3 게임 플레이 모드

### MVP 필수 모드

**A. FREE FLIGHT**
- 소형 도심 구역 안에서 제한된 목표 없이 자유롭게 날 수 있다.
- 비행 시간, 총 거리, 최고 속도, 최고 고도를 기록한다.
- 충돌해도 즉시 게임 오버 처리하지 않는다. 근처 안전 지점 또는 마지막 체크포인트로 복귀시킨다.
- 구역 경계를 벗어나면 부드러운 안내와 복귀 유도를 제공한다.

**B. SKYLINE RUN**
- 도시에 배치된 체크포인트 링을 순서대로 통과하는 코스형 도전 모드다.
- 제한 시간, 통과한 링 수, 근접 회피, 충돌 수, 완주 여부를 점수화한다.
- 링 통과 순서와 다음 목표 방향을 HUD/월드 마커로 안내한다.
- 초반 코스는 넓고 쉬운 통로, 후반은 빌딩 사이의 좁은 통로와 장애물을 배치한다.

### 후속 확장(첫 버전에 구현하지 않아도 됨)

- TIME ATTACK: 최고 기록 갱신
- PRECISION: 충돌 없이 모든 링 통과
- WIND CHALLENGE: 횡풍·난기류 구역 통과
- NIGHT FLIGHT: 야간 도시 비행
- 기체 스킨/도장, 비행 흔적, 카메라 프리셋

첫 버전에서는 모드 수를 늘리기보다 FREE FLIGHT와 SKYLINE RUN의 완성도를 높인다.

# 2. 핵심 게임플레이 요구사항

## 2.1 비행기 조종

비행기는 Rigidbody 기반 물리로 이동시킨다. Transform을 매 프레임 직접 이동시켜 물리 계산을 우회하지 않는다.

필수 조작 축:

- Pitch: 기수 상승/하강
- Roll: 좌우 날개 기울이기
- Yaw: 기수 좌우 회전
- Throttle: 엔진 출력/속도 제어
- Boost: 제한 시간 동안 추가 추진력
- Air Brake: 감속 및 정교한 접근

기본 조작은 다음과 같이 설계한다.

- 좌측 가상 조이스틱 X축: Roll
- 좌측 가상 조이스틱 Y축: Pitch
- 우측 버튼: Boost, Air Brake, 카메라 전환, 재정렬/복귀
- 기본 비행에서는 기체가 기울어진 방향으로 자연스럽게 선회하도록 자동 협조 선회(yaw assist)를 제공한다.
- 고급 조작 옵션에서는 Rudder/Yaw를 별도로 조절할 수 있게 구조를 열어둔다.
- 가속/감속은 기본적으로 자동 순항 속도를 제공하고, 별도의 스로틀 입력으로 속도를 조절하는 방식을 적용한다. 단, 화면이 복잡해지면 MVP에서는 속도 제어를 단순화할 수 있다.
- 휴대폰 자이로 조작은 선택 옵션으로만 추가한다. 기본값은 터치 조이스틱이다.

조작 UI는 모바일 가로 화면에 최적화한다. 터치 영역이 너무 작지 않도록 하고, 오른손 버튼은 엄지 도달 범위를 고려한다. 조이스틱은 드래그 시작 위치를 중심으로 하는 플로팅 방식 또는 고정 방식 중 실제 기기 테스트에서 더 안정적인 쪽을 선택한다.

## 2.2 비행 물리 모델

현실적인 인상을 주는 간소화된 에어로다이내믹 모델을 구현한다.

- Rigidbody의 질량, 선형 속도, 각속도, 관성 텐서를 활용한다.
- 엔진 추진력은 기체 전방 방향으로 가한다.
- 양력은 속도, 날개 방향, 받음각을 기반으로 계산한다.
- 항력은 속도 제곱에 비례하는 기본 모델로 구현한다.
- 중력은 Rigidbody에 자연스럽게 적용한다.
- Roll 입력으로 기체가 기울어지고, 기울어진 양력 방향으로 선회가 발생해야 한다.
- Pitch 입력은 기수의 상승/하강을 유도하되, 속도 부족 상태에서는 양력이 약해지는 느낌이 나야 한다.
- Yaw는 방향 안정화와 협조 선회를 보조한다. Roll 없이 기수가 순간적으로 옆으로 튀는 현상을 방지한다.
- 속도가 빠를수록 조종 반응이 지나치게 민감해지지 않도록 속도별 조종 권한을 조절한다.
- 공기 저항, 각속도 감쇠, 기체 안정화 보조력을 적용해 조작에서 손을 놓았을 때 기체가 무한히 회전하지 않도록 한다.
- 실속(Stall)은 첫 버전에서 복잡한 실속 시뮬레이션 대신 저속에서 양력이 감소하고 기수가 천천히 떨어지는 정도로 표현한다.
- Boost는 부스트 게이지 또는 쿨다운을 적용한다. 상시 무제한 부스트는 금지한다.
- Air Brake는 항력을 크게 높여 속도를 줄이며, 저속에서 조종이 불안정해지지 않도록 최소 속도 보조를 둔다.

**구현 가이드**

- `FixedUpdate()`에서 힘과 토크를 계산한다.
- 비행 속도는 `Rigidbody.velocity` 또는 해당 Unity 6 API의 변경 사항을 확인한 현재 권장 속성으로 가져온다.
- `AddForce`, `AddRelativeTorque` 등 Rigidbody 물리 API를 우선 사용한다.
- 입력 수신은 Update 단계에서 처리하고 물리 계산용 입력값은 FixedUpdate에서 소비한다.
- `Time.deltaTime`과 `Time.fixedDeltaTime`을 혼동하지 않는다.
- `Rigidbody.interpolation`을 활성화하고 Fixed Timestep을 적절히 설정한다.
- 물리 파라미터를 코드에 하드코딩하지 말고 `[SerializeField]`로 노출하거나 ScriptableObject 설정값으로 분리한다.
- `AircraftFlightTuning` 같은 설정 에셋을 통해 추력, 양력, 항력, 피치/롤/요 토크, 감쇠, 최대 속도, 부스트 값을 조정할 수 있어야 한다.
- 수치를 정한 뒤 반드시 실제 플레이로 조작 방향과 반응을 확인한다. 입력 부호가 반대거나 기체 축이 잘못된 경우 수정한다.

### 조작감 승인 기준

- 조작 입력과 기체 반응 사이에 과도한 지연이 없어야 한다.
- 좌우 입력 시 기체가 먼저 기울고, 그 기울기에 따라 선회한다.
- 기체가 즉시 방향을 뒤집는 드론 같은 느낌이 아니어야 한다.
- 입력을 놓았을 때 감쇠가 자연스럽고, 계속 흔들리거나 급격히 원위치로 튕기지 않아야 한다.
- 좁은 빌딩 사이를 통과할 때 미세 조정이 가능해야 한다.
- 속도를 올리면 체감상 빠르게 느껴지되, 화면 흔들림 때문에 조작이 불가능해지면 안 된다.
- 초보자도 1~2분 안에 기본 상승·하강·선회를 이해할 수 있어야 한다.

## 2.3 카메라

기본 카메라는 3인칭 Chase Camera다.

- 비행기 후방과 약간 위쪽에서 기체를 추적한다.
- 기체의 위치와 회전을 부드럽게 추적한다.
- 기체가 선회할 때 카메라도 약간 기울어져 속도감이 느껴지도록 한다.
- 속도에 따라 FOV를 미세하게 증가시킨다.
- 카메라 흔들림은 충돌·난기류·부스트 시에만 절제해서 사용한다.
- 건물이나 장애물에 카메라가 파고들지 않도록 카메라 충돌 처리를 한다.
- 화면 회전/카메라 이동이 멀미를 일으킬 정도로 과하면 안 된다.
- 버튼으로 기본 추적 시점과 조종석 시점을 전환할 수 있도록 확장 가능하게 구현한다. 조종석 시점은 MVP에서 완성도가 부족하면 잠금 또는 후순위 처리한다.

## 2.4 충돌과 복귀

충돌 대상:

- 빌딩 외벽 및 옥상 구조물
- 크레인 붐/기둥
- 통신탑과 안테나
- 드론 및 비행 장애물
- 공중 링 프레임 또는 훈련용 장애물
- 지면과 기타 월드 경계

충돌 시:

- 충돌 지점에서 짧은 파티클/사운드/카메라 피드백을 제공한다.
- 충돌 횟수와 점수 패널티를 기록한다.
- 화면이 오래 흔들리거나 과도한 블러가 생기지 않도록 한다.
- 기체가 무한히 튕기거나 건물 안에 끼지 않도록 처리한다.
- 일정 시간 후 마지막 체크포인트 또는 안전한 고도/위치로 복귀한다.
- FREE FLIGHT에서는 재시작 강요 없이 부드럽게 복귀한다.
- SKYLINE RUN에서는 체크포인트 기준으로 재개하거나 짧은 시간 패널티를 준다.
- 일시정지·복귀·재시작은 어떤 상황에서도 정상 동작해야 한다.

충돌 판정은 `Collider`와 Rigidbody를 기반으로 한다. 건물의 모든 창문·장식물에 복잡한 MeshCollider를 적용하지 말고, 단순화된 BoxCollider/CapsuleCollider 등으로 성능을 관리한다.

## 2.5 장애물 디자인

최소 6가지 이상의 장애물 유형을 구현하거나 교체 가능한 구조로 설계한다.

1. **Checkpoint Ring:** 통과해야 하는 공중 게이트. 색상/빛으로 통과 가능 방향을 알려준다.
2. **Construction Crane:** 고정된 크레인 기둥과 회전/긴 붐 구조물.
3. **Survey Drone:** 정해진 경로로 이동하는 소형 드론.
4. **Billboard Frame:** 빌딩 사이 광고판 프레임 또는 통과 구역.
5. **Antenna Array:** 옥상 통신 안테나. 실루엣이 분명해야 한다.
6. **Skybridge:** 빌딩을 연결하는 다리. 통과 가능한 구멍 또는 상/하단 회피 경로를 제공한다.
7. **Cable Zone:** 잘 보이는 경고등/표식이 있는 공중 케이블. 시인성이 낮은 가느다란 선을 무작위로 배치하지 않는다.
8. **Moving Cargo / Balloon / Training Marker:** 후속 확장용 동적 장애물.

장애물은 플레이어가 예측하고 피할 수 있어야 한다. 화면에 거의 보이지 않는 장애물, 갑자기 나타나는 즉사형 장애물, 피할 공간이 없는 배치는 금지한다.

# 3. 도시 월드 및 레벨 설계

## 3.1 MVP 월드 범위

- 하나의 작은 도심 구역으로 시작한다. 무한 오픈월드를 만들지 않는다.
- 초기 기준 크기: 약 800m × 800m 내외의 압축된 도심 구역. 실제 기체 속도와 모바일 프레임에 따라 조정한다.
- 높이 범위와 비행 가능 고도를 설계해 빌딩 사이 저공 비행과 상공 자유 비행을 모두 가능하게 한다.
- 월드 끝은 바다·산·안개·낮은 지형 등으로 자연스럽게 처리한다.
- 플레이어가 구역 경계를 벗어나면 지도 안쪽으로 유도한다.
- 비행 코스는 빌딩 숲의 좁은 통로, 고층 빌딩 바깥쪽 회전, 크레인 회피, 링 연속 통과가 섞이도록 설계한다.

## 3.2 도시 구성

- 건물은 최소 10개 이상의 재사용 가능한 모듈/프리팹 변형으로 구성한다.
- 유리 빌딩, 콘크리트 빌딩, 저층 상업 건물, 옥상 설비, 크레인, 통신 구조물 등 실루엣을 구분한다.
- 건물 높이와 폭을 일정하게 반복하지 않는다.
- 가까운 건물은 창문, 프레임, 옥상 설비 등을 표현하고 원거리 건물은 단순화한다.
- 건물마다 수백 개의 독립 GameObject를 무작정 생성하지 않는다. Mesh 결합, GPU Instancing, LOD, 공유 머티리얼을 활용한다.
- 창문은 반복 메시/텍스처/셰이더로 처리해 드로우콜을 통제한다.
- 도시 레이아웃은 처음에는 수작업으로 설계하고, 필요할 때 Editor 기반 보조 생성기를 추가한다.
- 절차적 배치가 들어가더라도 랜덤이 플레이 공간을 막지 않게 Seed와 수동 조절 기능을 둔다.

## 3.3 레벨 구성

초기 코스는 최소 다음 구간을 포함한다.

1. **Takeoff Zone:** 조작 연습이 가능한 넓은 공간.
2. **First Towers:** 넓은 빌딩 사이를 지나가는 쉬운 코스.
3. **Narrow Canyon:** 좌우 건물 사이 좁은 통로를 통과한다.
4. **Crane Crossing:** 크레인 붐/기둥을 회피한다.
5. **Drone Corridor:** 이동 드론이 있는 구간.
6. **Skybridge Gate:** 공중 연결 구조물의 지정 구역을 통과한다.
7. **High Altitude Turn:** 높은 고도로 상승한 뒤 선회한다.
8. **Final Gate:** 마지막 링 통과 후 결승 지점으로 진입한다.

코스는 플레이어가 여러 경로를 선택할 수 있도록 가능한 구간에 대체 통과 공간을 제공한다. 단, 미션 모드에서 필수 링의 순서는 명확해야 한다.

## 3.4 체크포인트와 경계

- 시작 지점과 체크포인트의 위치/방향/회전값을 데이터로 관리한다.
- 재시작 시 기체가 건물이나 장애물 내부에서 생성되지 않아야 한다.
- 체크포인트는 플레이어가 다음 목표를 인지할 수 있는 시야를 확보한다.
- 월드 경계 처리에는 텔레포트만 사용하지 말고 안내 HUD, 경계 효과, 속도 제한 또는 복귀 유도 중 적절한 UX를 적용한다.

# 4. 점수·미션·기록

## 4.1 점수 항목

- 링 통과 점수
- 연속 링 콤보
- 장애물 근접 회피(Near Miss)
- 완주 보너스
- 남은 시간 보너스
- 충돌 패널티

점수 계산은 `ScoreCalculator` 또는 별도 서비스에 분리하고 단위 테스트를 작성한다.

## 4.2 근접 회피(Near Miss)

- 장애물과 일정 거리 이내를 충돌 없이 통과했을 때만 인정한다.
- 속도·근접도에 따라 보너스를 주되, 충돌 위험을 과도하게 유도하지 않는다.
- 한 장애물에서 짧은 시간 안에 점수가 여러 번 중복 발생하지 않도록 쿨다운/상태 플래그를 둔다.
- 플레이어가 실제로 회피했다고 느낄 수 있도록 짧은 HUD 피드백과 사운드를 제공한다.

## 4.3 로컬 기록

- 최고 점수, 최고 거리, 최고 속도, 최고 고도, 완주 시간, 설정을 기기에 저장한다.
- 계정, 클라우드, 로그인 없이 작동한다.
- 작은 설정/기록은 JSON 기반 로컬 저장으로 관리할 수 있다.
- 저장 데이터 버전 필드를 포함해 향후 구조 변경에 대비한다.
- 저장 실패 시 게임 플레이가 중단되지 않도록 기본값으로 복구한다.

# 6. 기술 스택 및 Unity 프로젝트 설정

## 6.1 기본 스택

- Unity **6.3 LTS**
- C#
- Universal Render Pipeline(URP)
- Unity Input System 또는 Unity EventSystem 기반 터치 입력. 프로젝트의 현재 패키지 버전과 호환성을 먼저 확인한다.
- Unity Physics / Rigidbody / Collider
- Unity Test Framework (EditMode 및 PlayMode 테스트)
- ScriptableObject 기반 비행/게임 밸런스 설정
- Android ARM64 빌드
- Google Play 배포용 Android App Bundle(AAB)

HDRP는 모바일 타깃에서 사용하지 않는다. 필요하지 않은 패키지/플러그인은 추가하지 않는다.

## 6.2 렌더링

- URP Asset을 생성하고 모바일 친화적으로 설정한다.
- 기본은 Forward Rendering 및 호환 가능한 모바일 그래픽 옵션을 사용한다.
- MSAA, Render Scale, Shadow Distance, Additional Lights, HDR 등은 중급 기기 성능을 기준으로 조절한다.
- 실시간 그림자는 태양광 1개 중심으로 제한한다.
- 건물과 장애물은 LODGroup과 공유 머티리얼을 사용한다.
- 파티클은 짧고 적은 수량으로 유지하며 Object Pooling을 적용한다.
- 텍스처는 모바일 해상도/압축 형식을 적용하고 지나치게 큰 원본을 그대로 포함하지 않는다.
- 모바일에서 지원하지 않는 셰이더/효과를 필수 기능으로 사용하지 않는다.

## 6.3 Android 빌드 기본값

Google Play 신규 앱 정책을 기준으로 설정하되, 제출 시점의 최신 정책을 다시 확인한다.

- Platform: Android
- Scripting Backend: IL2CPP
- Target Architectures: ARM64 우선
- Target API Level: **API 36 이상**을 기본 목표로 한다. Unity 6.3 LTS 및 Android SDK 설치 상태에서 실제 지원 여부를 확인한다.
- Minimum API Level: Unity 6.3 및 사용 기기 요구사항을 확인한 뒤 합리적인 값으로 설정한다. 무조건 가장 낮은 값을 선택하지 않는다.
- Build App Bundle: On (Google Play AAB)
- Orientation: Landscape
- Internet permission: 오프라인 MVP에서는 불필요하면 요청하지 않는다.
- 카메라, 위치, 연락처 등 게임에 필요 없는 민감 권한을 요청하지 않는다.
- 앱 이름, 아이콘, 패키지 ID, 버전 코드를 일관되게 관리한다.
- 샘플 Application Identifier: `com.logicphantom.towerglide` (실제 Play Console 등록 전 사용 가능 여부를 확인하고 필요하면 변경)
- Development Build/Script Debugging은 출시용 AAB에서 비활성화한다.

Google Play에 제출할 때 AAB를 사용한다. APK는 개발 기기에서 직접 설치/테스트할 때만 보조적으로 사용한다.

# 7. 무료 개발 및 라이선스 정책

## 7.1 비용 정책

**목표: Unity Personal과 무료 리소스를 이용해 추가 개발비를 최소화한다.**

- Unity Personal의 최신 자격 기준을 확인한다. 현재 공식 기준은 최근 12개월의 관련 매출/자금이 미화 20만 달러 미만인 개인·소규모 조직 등에 해당한다. 기준이 변경되면 공식 약관을 따른다.
- Unity Personal은 무료지만, Google Play 개발자 계정 등록에는 별도 25 USD 1회 등록 비용이 있다. 이 프로젝트를 “완전히 비용 0원으로 게시할 수 있다”고 표현하지 않는다.
- Google Play 수수료, 환전/세금, 유료 에셋, 외부 서비스 비용은 별도다.
- 유료 Asset Store 에셋, 유료 Unity 플랜, 구독형 AI/모델/텍스처 생성, 유료 서버·API는 사용하지 않는다.
- 외부 에셋이 없어도 게임이 실행되도록 기본 비행기·건물·링·장애물은 프로시저럴 메시 또는 Unity 기본 메시로 생성 가능한 대체 경로를 둔다.

- 제작자
- 공식 출처 URL
- 가격(무료 여부)
- 라이선스 이름 및 링크
- 상업적 사용 허용 여부
- 수정 가능 여부
- 저작자 표시 의무
- 배포/재배포 제한

라이선스 정보가 불명확하면 에셋을 제외한다. Kenney 에셋을 사용할 때도 무료 개별 다운로드인지, 해당 에셋 페이지가 CC0인지 확인한다. 유료 All-in-1 번들을 무료라고 가정하지 않는다.

# 9. 씬 및 자동 생성

## 9.1 씬

- `Boot`: 초기 설정, 저장 데이터 로드, MainMenu 진입
- `MainMenu`: 비행기와 도시 배경, 게임 모드 선택
- `CityFlight`: 실제 비행 플레이

MVP 구현 시 `Boot`와 `MainMenu`를 통합할 수 있으나 상태 관리가 혼란스럽지 않아야 한다.

## 9.2 Editor 자동화

`Assets/_Project/Editor/` 아래에 다음 자동화 도구를 만든다.

- `TowerglideProjectSetup`: 폴더/레이어/태그/URP 설정 확인
- `TowerglideSceneBuilder`: 필수 씬과 기본 카메라·조명·UI Canvas·비행기·도시 프리팹 배치
- `TowerglideAndroidBuild`: Android 빌드 설정 검증 및 AAB 빌드 메뉴

Editor 스크립트는 중복 실행해도 오브젝트가 무한히 추가되지 않도록 멱등성을 확보한다. 씬을 자동 생성하는 경우 생성 결과와 수동 조정 포인트를 문서화한다.

**중요:** Claude Code가 Unity Editor를 실제 실행하지 못했으면 씬 파일이 정상 생성되었다고 단정하지 않는다. 생성 도구의 코드 작성과 실제 Unity 실행/씬 생성은 구분한다.

# 10. 성능 및 모바일 최적화

## 10.1 목표

- 중급 Android 기기에서 안정적인 30 FPS 이상
- 최신/상위 기기에서는 60 FPS 목표
- 프레임 타임의 급격한 스파이크 최소화
- 터치 입력 지연 최소화
- 장시간 비행 시 메모리 증가/GC 스파이크 방지
- 과도한 초기 로딩과 앱 크기 억제

성능 수치는 목표이며 실제 기기 측정 결과로 검증한다. 측정하지 않은 성능을 보장하지 않는다.

## 10.2 최적화 지침

- Update/FixedUpdate에서 불필요한 LINQ, 반복적인 문자열 생성, 과도한 GetComponent 호출을 피한다.
- 자주 사용하는 컴포넌트 참조는 초기화 시 캐싱한다.
- 파티클, 링 이펙트, 반복 장애물은 Object Pooling을 적용한다.
- 빌딩·장애물 재질 공유 및 GPU Instancing을 적용한다.
- 건물 LOD와 원거리 단순화 적용
- 불필요한 실시간 그림자·반사·투명 재질 제한
- Overdraw를 유발하는 UI/파티클 제한
- 가능하면 정적 도시 오브젝트는 Static 처리 및 적절한 Occlusion Culling 검토
- 실시간으로 움직이는 오브젝트의 수를 제한한다.
- 텍스처 최대 크기와 압축 설정을 관리한다.
- 앱 포커스가 사라지거나 백그라운드로 가면 게임을 일시정지하고 사운드를 낮추거나 중지한다.
- 발열·배터리 소모를 고려해 프레임 제한/품질 옵션을 제공한다.

## 10.3 프로파일링

- Unity Profiler로 CPU, GPU, Memory, GC Alloc을 확인한다.
- Android 실기기에서 Development Build와 Release Build를 구분해 측정한다.
- 가능한 경우 Android GPU Inspector 등 무료 공식 도구를 사용하되 필수 의존성으로 만들지 않는다.
- 성능 측정 결과를 `docs/PERFORMANCE.md`에 기기, 해상도, 그래픽 옵션, FPS, 메모리와 함께 기록한다.

# 11. 테스트 요구사항

## 11.1 EditMode 단위 테스트

최소 다음 항목을 테스트한다.

- 입력값 정규화와 Dead Zone
- 비행 속도/고도 표시값 변환
- 점수 계산과 충돌 패널티
- 링 통과 중복 판정 방지
- 체크포인트 순서와 진행률
- 부스트 게이지/쿨다운 경계값
- 저장 데이터 직렬화/역직렬화
- 손상되거나 누락된 저장 데이터 기본값 복구

## 11.2 PlayMode 테스트

- 게임 시작 시 비행기가 정상 스폰되는지
- Rigidbody가 활성화되어 있는지
- 입력을 주면 속도/방향이 예상 방향으로 변하는지
- 입력을 놓았을 때 각속도가 안정화되는지
- 빌딩/장애물 충돌이 처리되는지
- 체크포인트를 통과하면 진행률이 증가하는지
- 충돌 후 안전한 위치로 복귀하는지
- 일시정지/재개가 입력과 물리를 정상 제어하는지
- 결과 화면 진입 후 다시 시작할 수 있는지

## 11.3 실기기 수동 테스트

최소 확인 항목:

- 저사양/중급/고급 Android 기기에서 설치 및 실행
- 가로 화면 방향 고정
- 조이스틱과 버튼이 화면 비율에 맞게 배치되는지
- 터치 조작이 실제로 편하고 오입력이 적은지
- 5분 이상 플레이 시 프레임 저하/발열/메모리 증가 확인
- 앱 백그라운드 전환 후 복귀
- 사운드 포커스 및 진동 권한 동작
- 게임 중 시스템 UI/노치와 HUD 충돌 여부

- 모든 에셋 라이선스 기록 완료
- 아직 제출하지 않았다면 “출시 준비 완료”와 “실제 Play Console 게시 완료”를 구분해 보고

# 13. 출시 정책 및 Google Play 체크리스트

- Google Play 신규 앱은 현재 정책상 Android 16(API 36) 이상을 타겟팅해야 하는 시점인지 제출 직전에 공식 문서에서 다시 확인한다. 정책 변경 가능성이 있으므로 API 값을 영구적으로 고정하지 않는다.
- Google Play 제출 포맷은 Android App Bundle(AAB)을 사용한다.
- 개인 개발자 계정이 2023년 11월 13일 이후 만들어졌다면, 프로덕션 액세스 전에 최소 12명의 테스터가 연속 14일 이상 비공개 테스트에 참여해야 하는 요구사항이 적용되는지 확인한다.
- Play Console 계정 등록비는 USD 25 일회성으로 별도 책정한다.
- 데이터 수집이 없는 오프라인 게임이라도 Google Play Data Safety, 개인정보처리방침, 콘텐츠 등급, 광고 여부 질문을 실제 앱 동작에 맞게 답변한다.
- 분석/광고/로그인/클라우드 기능을 추가하지 않았다면 관련 권한과 SDK가 패키지에 들어가지 않았는지 확인한다.
- 사용하지 않는 권한을 AndroidManifest에 포함하지 않는다.
- 업로드 키/서명키를 Git에 커밋하지 않는다. `.gitignore`와 별도 백업 방식을 안내한다.
- 앱 제목과 패키지 ID, 아이콘, 스크린샷, 설명이 서로 일치해야 한다.
- 실제 플레이 장면을 캡처해 스토어 이미지로 사용한다. 구현되지 않은 기능을 스토어 문안에 쓰지 않는다.

# 14. 기본 밸런스 초깃값(실제 플레이로 조정할 것)

아래 값은 시작점일 뿐 정답이 아니다. 기체 스케일·질량·Rigidbody 단위·힘 계산에 맞게 조정하고 `AircraftFlightTuning`에 저장한다.

- 기본 자동 순항 속도: 약 90~120 km/h 체감 범위에서 시작
- 일반 최고 속도: 약 220~260 km/h 범위에서 시작
- Boost 최고 속도: 일반 최고 속도보다 제한적으로 높게 설정
- 최소 유효 비행 속도: 기체 반응과 월드 스케일에 맞춰 튜닝
- Roll 최대 기울기: 초보자 모드에서는 제한, 고급 설정에서는 확장
- Pitch 입력: 너무 민감하지 않게 커브 적용
- 조종 입력 감쇠: 입력 중 즉시 반응하되 놓으면 안정화
- 카메라 FOV: 기본값에서 속도에 따라 소폭만 증가
- Boost 사용 시간/회복 시간: 짧은 도전 구간을 통과할 정도로 제한

중요한 것은 숫자 자체가 아니라 플레이어가 체감하는 움직임이다. 속도 단위와 Unity 월드 단위(1 unit ≈ 1m 가정)를 일관되게 유지한다.

# 15. Claude Code 작업 규칙

1. 작업 시작 시 `README.md`, `WORKLOG.md`, `docs/DECISIONS.md`를 확인한다.
2. Unity 프로젝트가 없으면 `Assets`, `Packages`, `ProjectSettings` 등 정상 Unity 구조를 생성한다. Unity Editor 버전과 패키지 호환성을 먼저 확인한다.
3. 가능한 경우 C# 코드를 작성한 뒤 Unity Batch Mode로 컴파일/테스트한다. 실행할 Unity Editor 경로를 확인하지 못하면 무작정 임의 경로로 실행하지 않는다.
4. 새 클래스를 만들 때 파일명과 public class명을 일치시킨다.
5. Null 참조, 씬 오브젝트 누락, 프리팹 연결 누락을 방지하기 위해 Inspector 필드 검증과 명확한 오류 로그를 둔다.
6. 런타임 생성 오브젝트는 반복 생성/해제 비용을 고려하고, 필요한 경우 Object Pooling을 사용한다.
7. 비행 물리와 입력을 같은 클래스에 뒤섞지 않는다.
8. UI 이벤트가 비행 물리에 직접 접근하지 않고 Input Router를 통해 전달되도록 한다.
9. 스크립트가 씬에 연결되지 않은 상태를 방치하지 않는다. Editor Setup 도구 또는 정확한 수동 설정 문서를 제공한다.
10. 실행 불가능한 임시 코드는 `TODO`만 남기고 완료 처리하지 않는다.
11. 새 패키지 설치가 필요하면 공식 Unity Package Registry 여부와 라이선스를 확인한다.
12. 사용자 승인 없이 유료 서비스, 계정, 외부 API, 광고 SDK를 추가하지 않는다.
13. 각 단계의 변경 파일, 테스트 결과, 알려진 문제, 수동 작업을 `WORKLOG.md`에 기록한다.
14. 컴파일 오류와 경고를 가능한 한 해결하고, 남은 경고는 이유를 기록한다.
15. 중요한 물리 상수와 레벨 데이터는 코드 깊숙이 하드코딩하지 않고 설정 파일/ScriptableObject로 분리한다.
16. 성능과 조작감 검증은 실제 Android 기기 측정과 에디터 테스트를 구분한다.

## 15.1 첫 실행 시 Claude Code가 해야 할 일

다음 순서로 즉시 진행한다.

1. 현재 디렉터리와 프로젝트 파일을 확인한다.
2. Unity 6.3 LTS 및 Android 빌드 모듈 존재 여부를 확인한다.
3. 기존 프로젝트가 있다면 어떤 Unity 버전/렌더 파이프라인/패키지를 쓰는지 파악한다.
4. 프로젝트가 비어 있다면 `TOWERGLIDE` Unity 프로젝트 구조와 기본 문서를 만든다.
5. `docs/DECISIONS.md`에 Unity 버전, 렌더 파이프라인, 입력 방식, 저장 방식, 외부 의존성 결정을 기록한다.
6. Phase 1 Flight Feel POC를 먼저 구현한다.
7. 실제 실행 가능한 테스트를 수행하고 오류를 수정한다.
8. 현재 단계가 완료되면 다음 단계로 진행한다. 환경상 중단해야 할 때는 정확한 이유와 수동 실행 방법을 남긴다.

- [ ] 앱 백그라운드 전환 시 일시정지/사운드 처리가 정상이다.

- [ ] 실제 기기에서 FPS, 발열, 메모리를 측정했다.
